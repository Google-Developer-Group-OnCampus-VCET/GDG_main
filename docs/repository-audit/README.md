# Repository Intelligence Audit — `gdg` (GDG on Campus VCET)

This directory is a read-only technical audit of the repository, generated by walking the actual source code (not inferred from naming conventions or prior docs). It was produced by **seven parallel sub-agents**, each owning a disjoint slice of the 16 required files below; each sub-agent independently re-derived facts from source rather than trusting the pre-existing `docs/*.md` files, so some findings here may update or contradict those older documents.

## Project Summary

The repo started as a static marketing site for the GDG on Campus VCET student chapter (per `CLAUDE.md`'s brand/content rules) and was extended, in commit `c4ada08`, into a self-contained multi-event workshop operations platform: public registration, QR check-in, certificate issuance/verification, speaker/sponsor/agenda management, announcements, and a role-permission model — all backed by a single file-based SQLite database (`data/gdg.db`, via Node's built-in `node:sqlite`) with no ORM and no external services. It runs as one Next.js 16 App Router process; there is no separate backend server. Despite `docs/MULTI_TENANCY.md`'s framing, the running system is **single-tenant**: every code path hardcodes `chapter_id = "gdg-vcet"`.

The single most consequential finding of this audit (independently re-confirmed by at least two sub-agents reading different files) is that **the admin panel and its API routes have no authentication or authorization enforcement wired in** — no `middleware.ts` exists anywhere in the repo, `src/app/admin/layout.tsx` and `src/app/admin/page.tsx` perform no session check, and the sampled admin API routes (`/api/admin/events`, `/api/admin/registrations`) call database functions directly with no cookie/session validation despite a working session-cookie auth system (`src/lib/auth/index.ts`) and a defined-but-unused permission matrix (`src/lib/auth/roles.ts`) existing elsewhere in the codebase. Full severity classification is in `10-security-audit.md`.

## Important Caveats

- **Environment**: audited on a Windows 11 development machine; the database is a local file (`data/gdg.db`) using Node's experimental built-in `node:sqlite` module, not a managed/hosted database.
- **No browser automation was run** — this audit is static code analysis only, consistent with `CLAUDE.md`'s "Known gaps" note that no browser tool is available in this environment. No visual/accessibility/live-request verification was performed.
- **Pre-existing docs vs. this audit**: `docs/ARCHITECTURE.md`, `docs/API_REFERENCE.md`, `docs/DATABASE_SCHEMA.md`, `docs/DEPLOYMENT.md`, `docs/MULTI_TENANCY.md`, `docs/ROLE_PERMISSIONS.md`, `docs/IMPLEMENTATION_STATUS.md`, `docs/PROJECT_AUDIT.md`, `docs/FEATURE_TRACEABILITY.md`, and `docs/IMPLEMENTATION_PLAN.md` already existed before this audit. This audit treats them as unverified prior art and re-derives claims from source; where this audit and those docs disagree, trust this audit's cited file/line evidence, or re-check yourself.
- **Parallel authorship**: because 7 sub-agents worked concurrently on disjoint files, minor duplication of the same finding (e.g. the missing-auth issue) may appear across multiple files. This is intentional redundancy for evidence strength, not an error.
- **No secrets were copied into these docs.** Where a seeded credential or similar sensitive-looking value appears in application source as plaintext (e.g. a demo password seeded into the database at app boot), its existence and file/line location is noted as a finding, but treat any such value as already compromised/demo-only — rotate it before any real deployment rather than treating its disclosure here as the issue.
- **Scope boundary**: per the audit's strict rules, no application source code was modified, refactored, or deleted. Every file created by this audit lives under `docs/repository-audit/`.
